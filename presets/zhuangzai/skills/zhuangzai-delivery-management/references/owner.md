# 业主关注与服务跟进

## 工作台首轮

默认近7个自然日。先取观看记录，pageSize=50，首轮最多2页；未取全就描述已查范围，不称全公司排名。按已取数据选5个工地，对其中最多3个补充问题或施工动态（每个只选与沟通最相关的一种数据），总计最多6次业务调用。不为每个对象同时查详情、阶段、问题和动态，不推断客户情绪。

按用户目标确定公司、工地或部门及观看时间窗口，缺省选择近7天并说明。`list_owner_viewing_records` 返回工地×业主×日的观看汇总；取全分页后按稳定工地 ID、业主标识（若返回）去重，观看次数用各行 viewCount 求和，观看天数按日期去重。未提供稳定业主 ID 时不以微信昵称当唯一身份，改为按记录或工地汇总。views 是观看明细，未返回时不要编造时间或摄像头。

用返回的 projectId 与 `list_projects`、`get_project_detail`、`list_issue_records`、`list_progress_updates` 按需关联，查该工地的近期动态、阶段和需要跟进的问题，再组织沟通材料。只有能核对工地 ID 才关联；关键词只是模糊筛选，不能用相似地址、业主昵称猜测身份。观看记录可能含已删除工地；当前无法访问工地时保留原始记录并单列，不能把它默认为在建或绕过权限重查。

- 区分业主观看、员工线上巡检、现场签到三种行为；看到“微信用户”只表示昵称未授权，不据此合并不同业主。
- 观看频次高低是互动记录，不代表满意度、不满、投诉风险或成交意向；无观看记录也不代表客户不关心。相同工地出现问题与观看只能说明同工地同时间范围有记录，不证明业主看到问题或因此观看。
- 问题汇总区分总量、待处理、待审核及其他状态；时间筛选的状态是查询时状态。结合具体信息提出“可以主动沟通哪些内容”，而不是捏造客户诉求；用户需要明确问题详情时再取单条详情或工地入口。
- 结果默认只包含必要的业主称呼、工地和次数；不自动向客户发送消息、不传出数据。输出范围与时间、事实和建议，失败或信息不可见不得写作零。

工具不可用或失败时按 [回退表](tool-fallbacks.md) 交付可完成部分，不将其他来源替代为缺失模块的结论。
