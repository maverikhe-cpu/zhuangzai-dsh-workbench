# 一起装派工管理分析

围绕工程负责人、派工员或客户提出的具体问题，使用一起装已授权的数据，找出需要协调的派工申请和工人安排。分析前读取 [派工数据与口径](dispatch-data.md)。工具参数、字段和分页以当前连接实际定义为准。

## 开始

1. 从用户要求确定公司、工地或部门、日期和需要的结果；公司或登录对象不明确时先确认，不擅自切换。用户未指定范围时先根据问题选择合适的范围并说明；重要范围无法合理确定时只问最关键的一项。
2. 使用当前宿主已授权的一起装 MCP，确认工具可用，按需调用派工申请、派工记录及工地工具。不要创建第二套 OAuth、复制令牌或依赖私人脚本和固定路径。若客户端定义缺少最新参数，提示刷新连接或在现有可调用范围内继续，不绕过用户权限。
3. 先查看工具支持的过滤和少量样本；聚合时逐页取得所需范围并核对总数、截断和错误。先缩小到问题相关的时间、工地、状态，避免逐工地全量扫描。需要临时处理大批数据时只在当前任务环境中操作，区分公司与查询范围，不将旧公司缓存混入新公司。

数据量较大时先用小页读取 `total` 估算页数，再在需要完整明细时按工具上限分批获取、保留页号及错误并及时汇总；不要以第一批冒充全量。先给用户已核对的范围内概览，列出未完成范围；连接或分页长期无进展时停止无界等待，说明卡点与已完成情况，避免反复建代理、读取配置或凭证。仅在有完整数据、去重及一致的时间状态口径后输出全公司缺口排名。上游可能在分页期间变动，遇到总数变化或重复记录要重新核对并说明。

## 缩短等待与可靠汇总

2026-11-10 已复测 `get_dispatch_gap_summary` 的月度范围：

- 只看总量传 `include=["totals"]`；看排名只请求所需分组并用 `groupTopN`，不能对 totals-only 传 groupTopN。未选择的响应段不存在，不表示没有数据。
- Top N 仅裁剪分组输出，不改变 totals；截断后的分组和不能拿来与全量 totals 对账。`pageSize` 只控制 applications 明细，不缩小服务端汇总范围。
- 保留 `companyScope`、`effectiveFilters`、`queriedAt`，部门树根节点名不能替代公司身份。人数仍为跨申请求和。
- 大范围先明确日期，不默认无日期全历史。独立测试中全历史约61秒 internal_error，未返回文档所述25秒预算提示；缩小响应体并不消除后端全量取数成本。分月查询只覆盖实际取得的日期范围，不能省略未知或未查时段。
- 宿主把长响应转存本次结果文件时，先读取该明确文件引用，不把转存误判成接口失败。


- 先确认实时 MCP 是否已有可用的派工缺口汇总能力；如有，按实际 schema 使用汇总并按需下钻明细。没有就使用 `list_dispatch_applications`，不要假设或虚构新工具。
- 在等待全量明细时尽快说明申请总量及查询范围；仅用有数据支持的统计作阶段性结论，不将状态为待派工的数量当全部缺口。除非用户需要完整明细，先给重点工地、工种和下一步，完整明细按需生成。
- 当宿主能将**本次同一授权公司、同一查询条件**的每页原始 JSON 安全保存到当前工作目录时，可用 `python3 <技能目录>/scripts/summarize_dispatch.py pages.json --output summary.json` 做确定性去重、逐单缺口与工地/工种汇总。输入是 `{ "pages": [工具返回的分页对象, ...] }`；脚本拒绝缺页、重复申请 ID、页数或 total 不一致的输入，异常人数和未知状态单列。只用本次任务的结果，不扫描其他会话或历史日志，也不读取凭证。宿主明确提供的本次工具结果文件引用也可用；小页没有文件引用时不可通过扫描日志补齐。工具结果无法完整保存或计算时说明未完成范围，不自建代理；新接口有服务端汇总则优先使用。
- 汇总需求与已派是逐申请人数之和，不能称跨申请去重人数；缺口须逐申请取非负差再求和，不能用总需求减总已派抵消不同申请的超配。数据是查询时状态；按提交日期选出的旧申请并不自动代表当前仍需紧急派工。

## 从问题组织结果

- **需求和缺口**：以申请为单位列工地、工种、计划开工、需求人数、已派人数、缺口及申请状态；按工种或日期汇总。判断缺口先排除已拒绝或撤销申请，人数为空或为零时单列。紧急程度按计划时间与当前状态说明，不自动认定工地停工。
- **接单和进场安排**：以工人为单位列申请、工地、工种、状态、计划进离场；按需要列待接单、拒单或取消及今天到场。计划时间重叠只作为待核实的潜在撞期；排除取消、拒单，并用稳定工人 ID 匹配。记录工具日期范围是计划进场日，不能直接等同日期区间内所有在场工人。
- **施工面积**：并列显示申请预估面积及该派工记录独立维护的施工/结算面积，单位㎡；没有值显示未填写或未返回，不当作 0。它们与工地房屋/装修面积不同。多工人或多工种面积不直接相加，除非客户明确业务口径且能排除重复。
- **派工响应**：工具有 `includeStatusTimes` 时可针对少量具体申请查询接单/取消时间；结合可靠的对应派工时间才可算响应时长。申请拒绝、撤销、历史到场等无对应数据时不虚构时间线。
- **业务报告**：用户需要日报、周报、月报时，围绕申请 → 派工 → 接单 → 进场 → 日常监督组织；按需求展示分布和可核对明细。分母、时间维度、取消和重复记录的处理与客户先对齐；不能把实时状态当历史当日快照。

输出先回答用户的管理问题，再按需要给清单、汇总与建议；说明查询范围、取数时间和使用的日期口径。没有数据、未填写、字段不可用和查询失败分开处理。可生成 Markdown、Excel 或用户指定的报告；默认只查询与制作文件，不派工、不改记录、不发送消息。

派工结论交付前核对：`actual.days=0` 只表示现场识别记录天数为零；`arrivalToday` 未返回表示不可见。两者都不能推断实际未到场或到场人数为零；待接单、已派工、现场识别各按原字段分别描述。

**待接单与实际到场：** 待接单只表示系统中工人尚未确认接单，不代表人未到现场、不代表不可能出现现场识别记录。解释、表格和建议中都不能说待接单就没进场、没记录是必然结果。实际是否到场须有独立证据或现场核实。

分页续取、计算通路、重复核对与端到端计时遵循 [大任务方法](performance.md)。
