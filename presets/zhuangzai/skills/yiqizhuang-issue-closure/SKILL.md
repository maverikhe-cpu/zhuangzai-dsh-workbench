# 工地问题整改分析

围绕谁需要跟进、处理到哪一步和哪些问题需要复核组织结果。使用当前授权的一起装 MCP，以实时工具定义为准；先确认公司、范围、时间，缺省范围及时间须清楚说明。优先 `list_issue_records` 取六态问题明细；具体工地和个案按需用 `list_issues`、`get_issue_detail`。筛选发生日期得到的是这批问题的当前状态，不是历史时点快照；分页统计需取全并核对。关键词是模糊筛选，核对返回工地 ID 后再聚合，不能把姓名或地址近似当作精确关联。

- 分开统计待处理、进行中、被驳回、已整改待审核、审核通过，以及误判和非工作人员；驳回须重新处理，待审核未闭环。`auditStatusLabel` 省略代表该公司未启用审核时，已整改可视为闭环。申诉状态单列，不覆盖整改状态。
- `list_issues` 只有四态，工地 `issueCount` 是问题总量而非待处理数；跨工地全量或闭环分母用六态明细。是否将误判和非工作人员纳入分母按客户口径说明；分母为零不计算比率。
- 交付前核对各状态数字与总数的加总及文字是否一致，尤其不要把“总数 34、待处理 0”表述为两者相等。审核待处理和整改待处理是不同待办，分别给出。
- 整改期限和超时字段依赖公司配置，缺失不等于未超时。当前状态不可冒充某历史日期状态，也不把问题创建时间当整改完成时间。系统生成节点逾期问题与人工或视觉发现的质量安全问题分开；不能把同一个逾期节点和自动问题当两项独立事件。
- 输出优先事项：工地、具体问题、负责人（返回可见时）、状态、发现时间及整改期限、下一步；有工地问题页链接时附上。问题页是工地级入口，不声称可直接打开单条问题。无法归属负责人或因果时如实说明，建议核实而不虚构责任。
