# 2026-11-12 工作台场景入口实测

## 结论

工作台共有 8 个场景分类、20 个示例问题和 2 个推荐入口。22 个问题的前端路由检查通过：原问题完整传入、使用 zhuangzai 预设、草稿追加策略正确。桌面端从工作台实际发起 10 个独立场景（8 类各首题及 2 个推荐入口），全部进入装仔会话并加载综合技能。9 个场景读取对应场景方法文件；现场场景未读取 visibility.md。本次不判为整体验收通过。

## 环境与方法

- 本机 DSH 桌面版已启用的 0.5.3 测试包；DeepSeek-V4.1-Flash / High；已有真实公司授权。
- 此测试包与 0.5.3 正式包的代理、角色一致；主技能少了正式包最后强化的重试耗尽停止条款。没有把两者记为完全相同。
- 从真实工作台点击示例问题、新建装仔会话并发送，查看技能、引用文件及业务工具轨迹。没有用另一个客户端的 MCP 结果冒充桌面入口实测。
- 多个测试会话存在执行时间重叠，以下是各会话界面显示的端到端时长，不作为串行性能基准。工期任务有人工停止及后台任务完成后续写，单独记录，不给出连续完成时长。
- 本文不保存客户明细、原始聊天及认证信息。

## 场景结果

| 入口 | 实际技能方法 | 桌面显示耗时 | 结果 |
|---|---|---|---|
| 今天先关注哪里 | 综合技能 + priorities 兼容入口 + priorities.md | 3分29秒 | 能综合问题/工期，但额外查询无日期派工，超时后才收窄 |
| 生成管理汇报 | 综合技能 + report.md、data-and-metrics.md、company-policy.md | 3分55秒 | 正确识别上个月并组织月报；不是固定格式导出验收 |
| 管工地：我负责的在建工地 | 综合技能 + priorities.md | 3分21秒 | 方法匹配，但将授权全公司范围写成“你负责”，未验证个人负责范围 |
| 管人员：派工缺口 | dispatch 兼容入口 + 综合技能 + dispatch.md | 2分46秒 | 能调用派工缺口路径；需进一步收紧默认范围和下钻规模 |
| 管问题：最近问题跟进 | 综合技能 + issues.md | 4分52秒 | 方法匹配，但把最近问题扩成全历史状态/分类盘点、多次验证和下钻 |
| 管工期：阶段落后于计划 | 综合技能 + progress.md | 中途停止，后有续写 | 自动扫描全公司、启动6个助手，批量和分页成本失控；不是入口轻量路径 |
| 管质量：节点/报告跟进 | 综合技能 + acceptance.md | 4分1秒 | 调用报告和待验节点；逐工地抽查16个均无计划后，回答扩大成全公司未启用计划，推断超范围 |
| 管现场：现场问题与画面 | 综合技能，未读 visibility.md | 3分51秒 | 能取图并读图，但首次连接失败后搜索本地配置、猜域名、调用 shell 排查；偏离故障回退规则 |
| 管设备：在线情况关注 | 综合技能 + devices.md | 2分29秒 | 台账/在线率路径正确；自动扩展30天历史及较多明细，不是简单计数场景 |
| 管客户：业主关注与沟通 | owner 兼容入口 + 综合技能 + owner.md | 4分7秒 | 观看记录与工地/问题/动态关联可用；有较多对象下钻，适合再压缩首轮规模 |

这些时长属于复杂开放问题，不应与此前“列5个工地/设备计数/指定月份派工汇总”的42/42/67秒混在一起比较。

## 需要调整的地方

1. 入口提供明确、稳定的内部场景路由，让 Agent 先读对应方法；非简单查询不能只加载综合技能就自由展开。兼容入口仅用于旧调用，不必重复加载。
2. 首轮明确展示少量管理重点，先给结果；全公司全历史扫描、更多模块及大规模下钻作为用户可选择的后续任务。不能将少量样本冒充完整排名。
3. 管理重点默认只查问题、进度和现场；派工需要用户提出相关需求再加入。任何派工汇总在首个请求即设置合理日期语义，避免先全历史超时再收窄。
4. “我负责”必须识别当前操作者/负责人范围；识别不了就确认范围，不能将权限内全公司数据当成个人数据。待 get_company_context 实际上线后再验证能否支持身份匹配，工具名存在不等于能直接按个人筛选。
5. 故障后按错误信号停止；不自行猜域名、扫描配置或凭据。使用正式包强化后的主技能，并做可控故障回归。
6. 抽查结果只表述抽查对象；不能从16个工地无计划推断全公司无计划，也不能从部分状态推断整个处理流程停滞。
7. 全公司阶段风险适合工具侧提供筛选/汇总；现有按ID批量查询可用于重点对象，但不能靠多助手无限扩展替代成本控制。
